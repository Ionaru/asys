# One shared server, with an owner key on every record and Postgres row-level security

ASYS starts with a single User but is built as one server that can host several Users, each owning their data: every record carries its owner, and Postgres row-level security enforces the separation so a forgotten filter cannot leak one User's data to another. Retrofitting owner keys later would touch every table and query, and the long-term vision of collaboration within an organisation needs a shared server.

## Considered Options

- **One deployment and database per person**: simpler queries and no possible cross-user leak, but rejected because it rules out the collaboration vision.

## Consequences

Row-level security only holds when nothing bypasses it: the server and its workers connect as an app role that owns no tables and lacks BYPASSRLS, a separate role (with LOGIN) owns the tables and runs migrations, and every table also gets FORCE ROW LEVEL SECURITY (written as custom SQL, since Drizzle cannot emit it yet). The table-owning role is trusted: it can switch FORCE off on its own tables, so row-level security guards against the app role and against an accidental owner connection, not against migrations. The current owner is set per transaction (`set_config('app.owner_id', …, true)`) for both requests and background jobs, and every policy uses the one expression `owner_id = nullif(current_setting('app.owner_id', true), '')::uuid`; the `nullif` is required because a connection that has run such a transaction reads the setting back as `''`, not NULL, and `''::uuid` raises an error. Integration tests connected as the app role prove that one owner's reads and writes never reach another's (rejections asserted as SQLSTATE 42501), and that on a single pooled connection nothing of an owner remains visible after its transaction.

Some lookups happen before any owner is known: a passkey credential at sign-in, a session cookie, an API token, a Google account id, a Sign-up link, a Google Calendar push channel, and the job worker claiming due jobs across owners. Each goes through its own narrow `SECURITY DEFINER` function that takes the exact key and returns only the owner and the record id; the app role may execute these functions and nothing more, and policies never contain an "authenticating" escape clause. Because FORCE binds the table owner too, these functions cannot belong to it: they belong to a dedicated lookup role that cannot log in, has BYPASSRLS, owns no tables, and may select only each lookup's key and owner columns. The database bootstrap (as superuser) creates this role and grants it to the table owner `WITH INHERIT FALSE, SET TRUE`, so a migration can hand a new function over (`ALTER FUNCTION … OWNER TO`, with CREATE on the schema granted only for the handover). BYPASSRLS is never gained through membership, so the owner's own sessions stay bound by FORCE; changing or replacing a lookup function later means `SET ROLE` to the lookup role inside the migration.

Collaboration within an organisation will have to revisit the rule that every record has exactly one owner.
