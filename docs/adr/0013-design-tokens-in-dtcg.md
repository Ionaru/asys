# Design tokens in DTCG 2025.10, with one scheme modifier in a resolver

The design tokens in `libs/design-tokens/src` use the Design Tokens Community Group format (2025.10, Format and Resolver modules), so that a standard build tool can turn them into CSS later. Theme-independent tokens are in `base.tokens.json`, the Evergreen colours and sheet shadow of each theme are in `themes/*.tokens.json`, `scripts/palettes.mts` generates `palettes/<palette>-<theme>.tokens.json` for the other palettes, and a generated `asys.resolver.json` ties them together (the spec recommends the `.tokens.json` and `.resolver.json` extensions). The resolver has a `base` set and one `scheme` modifier with 12 contexts named `<palette>-<theme>`, default `evergreen-light`, because a palette is a full colour map per theme, so palette and theme are not independent choices. Palette and theme display names and each palette's ground live in the resolver, on the modifier's `$extensions` (the spec does not allow them at the resolver root), so adding a palette is one edit to `PALETTES` and one run of the script. Every extension uses the key `io.github.ionaru.asys`, the reverse domain of the project's GitHub home `ionaru.github.io`, as the spec recommends. Leaf names stay the CSS variable names (`paper`, `space-1`, `shadow-sheet`), so the font families are `font-sans` and `font-mono`, where the design system's own file keys them `sans` and `mono` and prefixes them when it compiles CSS.

Typography stays as the 18 `type-scale` dimension tokens, and the nine type styles live in the `typography` group's `$extensions` instead of being DTCG typography tokens. A 2025.10 typography composite needs a unitless line height and a px or rem letter spacing, but ours are rem line heights that the Line spacing setting rewrites and em letter spacings that deliberately scale with Text size; six of the nine ratios do not terminate, so converting would be lossy, would hold the line height in two places, and the composites would not follow the settings. The design system's components (its `bundle.css`) read the type-scale tokens and set weight and letter spacing in their own rules, and none uses a type style as one unit. Each palette file is a complete theme file, with every colour, its description and the shadow, and each context points at exactly one file: the resolver spec only says the last occurrence wins and does not say how a partial override merges with an earlier definition.

## Considered Options

- **Keeping the design system's own shape**: rejected because it is the thing being replaced: a custom grammar that no build tool reads.
- **Two modifiers, palette and theme, with an alias layer**: rejected because the authored colours would have to be restructured into per-palette roles that theme files alias, to express a choice that is not independent.
- **Typography composites with converted values**: rejected for the reasons above: lossy ratios, a duplicated line height, and em letter spacing that 2025.10 cannot express.
- **Palette files as partial overrides layered on the themes**: rejected because it relies on merge behaviour the resolver spec leaves undefined.
- **Palette names in each palette file**: rejected because each palette's name and ground would repeat in its three files, and Evergreen has no palette file, so its name would have to go into the hand-authored theme files that the artifact exports; in the resolver they sit once, next to the contexts that use them.

## Consequences

The build tool, Style Dictionary or Terrazzo, is deferred. Whichever is chosen must read the resolver, emit leaf names as the CSS variable names (`--paper`, `--space-1`, `--font-sans`), and handle the typography extension, whose `{…}` references DTCG tools leave as text, so it must resolve them and fail on a dangling one, and the `none` marker on drive's shadow, which DTCG cannot express. Terrazzo's resolved tokens leave out the token-less `typography` group, so a Terrazzo plugin would read it from the source documents. Terrazzo's `tz check` lints only the default context of each modifier, and accepts units other than px and rem and `$extensions` at the resolver root, which the official 2025.10 JSON schemas reject; so the 12 contexts were validated through Terrazzo's parser and every file against those schemas, with throwaway checks outside the repo, and the values were compared against the old files for all 4 palettes in 3 themes. A build step should run both checks.

The design system artifact cannot hold these files in its `tokens.json`: its page reads only its own grammar, so a DTCG file shows empty there and its entries are dropped at the first edit. It keeps that file, and exporting means converting it by the rules in the README, copying the result here and running the script; CI's `palettes` job fails when a generated file is stale.

Revisit this if a later DTCG version allows rem or em in typography composites, or if the design system artifact type learns DTCG, which would remove the conversion.
